# CUBR-0076 — the pre-registered gate for a web profile

**Written:** 2026-08-06 UTC, before any prototype exists or is measured.
**Task:** CUBR-0076 (web-profile prototype).
**Status:** gate statement only. No new threshold is proposed; nothing here is
renegotiated after a measurement, because the binding measurements predate this
document and the thresholds predate those measurements.

## The registered gate, verbatim from the DB

`web_benchmark_hypothesis` id **12** — axis `web_profile`, label
`web-profile-kill-gate`, task `CUBR-0076`, lifecycle `preregistered`,
created 2026-07-28 — with its criteria from
`web_benchmark_hypothesis_criterion` (ids 36–39):

| verdict | criterion | bar |
|---|---|---|
| WIN | `ratio_vs_brotli11` | ≤ 1.00 |
| WIN | `decode_throughput` | ≥ 200,000,000 B/s |
| GO | `ratio_vs_gzip9` | ≤ 1.00 |
| GO | `decode_throughput` | ≥ 50,000,000 B/s |

A web profile that cannot reach **50 MB/s whole-buffer decode at gzip-9
density parity** is killed by its own pre-registered gate. A web profile that
reaches **200 MB/s at brotli-11 density parity** wins outright.

## Lineage — how these bars relate to the 0.50 bar

The programme's existing decode bar is criterion **57** on hypothesis 11
(CUBR-0074): `decode_throughput_vs_brotli5 >= 0.50`, amended in place before
the CUBR-0074 measurement with a written derivation ("at most twice the decode
latency of the dynamic-response baseline"), with density deliberately left
against brotli-11. That two-baseline split is retained here unchanged:

- **density** is judged against brotli-11 (WIN) / gzip-9 (GO floor);
- **decode speed** is judged against brotli-5's class of service.

The absolute bars of hypothesis 12 are *laxer* than 0.50 × brotli-5:
brotli-5-class whole-buffer decode on web content runs at hundreds of MB/s, so
0.50 × brotli-5 sits above the 200 MB/s WIN bar, and far above the 50 MB/s GO
bar. The ordering that matters for interpretation, stated in advance:

1. **Failing hypothesis-12 GO (50 MB/s) is conclusive.** It is the laxest
   decode bar in the registered family; nothing that fails it can survive any
   stricter reading.
2. **Passing hypothesis-12 GO does not clear the product.** Product viability
   still requires re-evaluating hypothesis 11's `>= 0.50` on the same corpus
   and protocol. GO here means "the prototype direction is alive", not "ship".

The 0.50 bar itself is not renegotiated by this document. It was fixed in
advance of CUBR-0074's measurement, and CUBR-0074 measured `0.004410` against
it — a miss by 113×, not a near miss any browser-context argument could
close. No alternative bar is argued here, before or after measurement.

## Corpus and protocol

- **Corpus:** `bench/web-corpus/manifest.v2.json` (`cubr0074-web-real-v2`) —
  12/12 real samples, `real_world_sample_share` 1.0, per-sample SHA-256 in the
  manifest. The same corpus the 0.877644 density WIN was measured on. Known
  registered gaps (wasm — blocked on CUBR-0077; svg — operator sourcing
  decision) carry forward and are reported as gaps, never filled with
  fixtures.
- **Byte-exactness:** every observation requires a byte-exact round-trip
  (`cmp` after every decode). An observation without a passing round-trip is
  not an observation. This is the programme invariant; for hypothesis-12
  evaluation it is adopted explicitly as `roundtrip_exact_match_rate = 1`
  across all samples, in line with the criterion already registered for
  hypothesis 9.
- **Timing protocol:** decode throughput numbers that feed a verdict must be
  measured on a genuinely quiet host under the CUBR-0074 harness protocol
  (warmups, randomized schedule, pinning, admission checks). No such host is
  available to this lane today (see the ceiling document's recorded refusal),
  so this gate can be *stated* now but only *evaluated* when stand time
  exists.
- **DB discipline:** `web_benchmark_hypothesis_evaluation` stays at 0 rows
  until a candidate passes the reopen gates under that protocol. Voids stay in
  the journal.
