## Decode throughput — the gate cannot be adjudicated from this bundle

The bundle's raw durations give `decode_throughput_vs_brotli5 = 0.9764`, which
clears the `>= 0.50` bar. **That number must not be recorded as a pass.** It is
an artefact of the measurement method.

Median decode duration by sample size, for three codecs:

| sample bytes | gzip-9 | brotli-5 | cubrim-web |
|---|---|---|---|
| 9,700 | 3.360 ms | 3.823 ms | 3.586 ms |
| 55,431 | 3.877 ms | 3.901 ms | 4.409 ms |
| 320,976 | 4.917 ms | 4.522 ms | 4.653 ms |

A **33× increase in content adds about 1 ms.** Every codec sits on a floor of
3.5–4.1 ms that is subprocess spawn plus the systemd sandbox, and the decode
work itself is a sliver inside it. Because every codec pays the identical tax,
every ratio is dragged toward 1.0 — a codec decoding ten times slower than
brotli-5 would also have "passed".

Regressing median time on sample size separates the floor from the slope:

| codec | process floor | implied throughput | R² |
|---|---|---|---|
| gzip-9 | 3.477 ms | 226.8 MB/s | 0.855 |
| brotli-5 | 3.817 ms | 390.9 MB/s | 0.621 |
| cubrim-web | 3.950 ms | 476.0 MB/s | 0.528 |

That would give `1.2177` rather than `0.9764` — a different verdict from the
same trials. The slope estimate for Cubrim-Web (476 MB/s) is encouragingly
close to the 443 MB/s measured natively in `examples/web_decode_bench.rs`, but
**R² of 0.53 is not a measurement**, and neither figure should be published.

**Finding: the web benchmark measures compressed size correctly and cannot
measure decode throughput at all at web-asset sizes.** The five-metric protocol
times a subprocess per trial; at 10–320 KB the codec work is below the noise of
process creation. Fixing it needs an in-process timed loop — warm-up plus N
repeats divided by N — which is what the native harness already does and why it
can report 443 MB/s at all. Until then `decode_throughput_vs_brotli5` is
**unmeasurable in this channel**, and recording it as PASS would be a false
green of exactly the kind this epic keeps finding.

## AMENDMENT 2026-08-12 — "the only bar" is scope-dependent

Consequence 1 above says density "remains the only bar between the Web Profile
and a WIN". That is true only of `cubrim::decode` in the main crate.

`CUBR-0074-DECODE-INPROC-20260812.md` measures the decode gate in-process and
finds it has no single value: 0.7896 (PASS) for the main crate, 0.3603 (FAIL)
for the reference decoder in its shipped `opt-level="z"` build — the one the
WASM module wraps and a browser executes. The two are independent
implementations bound by a differential test, and the criterion never named
one.

Density is unaffected: the bytes do not care which decoder reads them. But for
the artefact that ships to browsers, density is *not* the only bar.
