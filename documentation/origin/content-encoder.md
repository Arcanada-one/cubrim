Cubrim можно использовать как HTTP-сжатие между сервером и браузером. Причём для первого прототипа не требуется менять сам HTTP-протокол: он уже допускает расширяемые алгоритмы сжатия через Accept-Encoding и Content-Encoding. Клиент сообщает поддерживаемые кодировки, сервер выбирает одну из них и обозначает её в ответе.

Например:

GET /app.js HTTP/2
Host: example.com
Accept-Encoding: cbm, br, gzip

Сервер отвечает:

HTTP/2 200
Content-Type: application/javascript
Content-Encoding: cbm
Vary: Accept-Encoding
Content-Length: 18234

Браузер получает тело, распаковывает его Cubrim и передаёт уже исходный JavaScript обычному HTML/JS-парсеру.

Я ниже использую рабочее имя cubrim. Для официального HTTP-токена можно выбрать короткий вариант вроде cbm, но позже его потребуется зарегистрировать.

Собственный Chromium сделать можно

Это вполне реалистичный эксперимент. Нужны две стороны.

1. Декодер Cubrim внутри Chromium

В Chromium потребуется добавить поддержку нового content coding:

Content-Encoding: cubrim

Работа примерно такая:

1. Встроить библиотеку декодирования Cubrim в C++-часть Chromium.
2. Добавить потоковый декодер в сетевой стек.
3. Научить браузер отправлять:

Accept-Encoding: cbm, zstd, br, gzip, deflate

4. Распознавать Content-Encoding: cbm.
5. Передавать распакованный поток дальше в Blink.
6. Добавить ограничения памяти, размера окна и времени декодирования.
7. Написать тесты на повреждённые и вредоносные потоки.

Менять HTML-движок, JavaScript-движок V8 или протокол HTTP/2/HTTP/3 не требуется. Изменяется в основном слой обработки HTTP-response body.

2. Серверная поддержка

На сервере нужен модуль или reverse proxy, который умеет:

* видеть Accept-Encoding: cbm;
* выбирать Cubrim только для поддерживающих клиентов;
* сжимать динамический ответ либо отдавать заранее сжатый файл;
* возвращаться к Brotli, Zstd или gzip для обычных браузеров.

Схема:

Origin application
↓
cubrim compression proxy
↓
HTTP/2 or HTTP/3
↓
Modified Chromium
↓
cubrim decoder
↓
HTML / CSS / JS / JSON

Самый быстрый вариант — не встраивать Cubrim сразу в Nginx, а сделать отдельный proxy-сервис:

Browser → cubrim proxy → Nginx/application

Он получает обычный ответ от приложения, сжимает тело Cubrim и добавляет соответствующий заголовок.

Что необходимо изменить в самом Cubrim

Здесь главная сложность. Хороший архиватор файлов ещё не обязательно является хорошим алгоритмом для веб-трафика.

Для браузера Cubrim потребуется отдельный профиль, условно:

Cubrim Web Profile

Потоковая распаковка

Браузер не должен ждать загрузки всего ответа.

HTML нужно начинать разбирать почти сразу:

получили первые байты
→ распаковали первый блок
→ начали строить DOM
→ продолжили загрузку

Следовательно, формат должен поддерживать:

* независимые или последовательно декодируемые блоки;
* небольшой заголовок;
* раннюю выдачу распакованных данных;
* отсутствие необходимости видеть конец файла;
* ограниченное состояние декодера.

Если текущий Cubrim сначала анализирует файл целиком, перебирает несколько методов и только затем создаёт архив, такой режим отлично подходит для предварительного сжатия статических ресурсов, но плохо подходит для динамических HTTP-ответов.

Очень быстрая распаковка

Для веба скорость декомпрессии зачастую важнее нескольких дополнительных процентов сжатия.

Пользователь не выиграет, если:

* Brotli передал 100 КБ и распаковался за 1 мс;
* Cubrim передал 85 КБ, но распаковывался 40 мс и заблокировал главный поток.

Декодирование должно:

* работать линейно;
* иметь предсказуемое потребление памяти;
* не производить большие аллокации;
* по возможности декодировать сотни мегабайт в секунду;
* хорошо работать на ARM-смартфонах;
* не выполнять сложный перебор моделей на клиенте.

Сложное сжатие на сервере допустимо. Сложная распаковка в браузере — значительно менее допустима.

Быстрый режим сжатия

Нужны как минимум два режима.

cubrim-static

Для заранее подготовленных JS, CSS, WASM, JSON и HTML:

* сжатие может занимать секунды или минуты;
* главное — минимальный размер;
* результат сохраняется рядом с оригиналом.

cubrim-dynamic

Для API и динамически создаваемого HTML:

* сжатие должно происходить почти в реальном времени;
* допустим немного худший коэффициент;
* крайне важны latency и CPU cost.

Brotli уже использует похожую практическую модель: высокий уровень для статических файлов и более быстрые уровни для динамических ответов.

Фреймированный формат

Для HTTP нужен стабильный битовый формат:

magic
version
flags
uncompressed-size optional
window-size
block type
block length
compressed payload
checksum

Желательно предусмотреть:

* версионирование;
* пропуск неизвестных необязательных секций;
* checksum каждого блока или всего потока;
* максимальный размер окна;
* детерминированное декодирование;
* чёткое поведение при обрыве;
* защиту от compression bombs.

У Zstandard, например, отдельно специфицированы frame headers, blocks и размеры окна, поскольку декодеру необходимо заранее понимать требования к памяти.

Жёсткие лимиты ресурсов

Браузерный декодер работает с недоверенными данными. Сервер может намеренно или случайно отправить поток, который:

* требует гигабайты памяти;
* чрезвычайно долго распаковывается;
* вызывает переполнение;
* создаёт огромный выход из нескольких байтов входа;
* зацикливает редкую модель декодирования.

Поэтому формат должен позволять браузеру установить:

max_window_size
max_output_size
max_expansion_ratio
max_dictionary_size
max_decoder_memory

А декодер должен быть написан как security-critical component с fuzzing, sanitizers и corpus-based testing.

Первый прототип можно сделать даже без форка Chromium

Есть более дешёвый путь для проверки идеи.

Вариант с JavaScript или WebAssembly

Сервер отдаёт файл, например:

Content-Type: application/cubrim

Страница загружает его через fetch(), декодирует Cubrim в WebAssembly и использует результат.

const response = await fetch("/data.cubrim");
const compressed = new Uint8Array(await response.arrayBuffer());
const decoded = cubrimDecode(compressed);

Это хорошо подходит для:

* JSON;
* больших наборов данных;
* моделей;
* игровых ресурсов;
* внутренних приложений;
* собственных SPA.

Но так нельзя прозрачно заменить HTTP-сжатие для первоначального HTML-документа: браузер должен сначала загрузить JavaScript/WASM-декодер. Также обычный <script src>, <link> и HTML parser не будут автоматически понимать такой формат.

Тем не менее это отличный нулевой этап, потому что позволяет измерить:

* реальное уменьшение трафика;
* время декодирования;
* стоимость CPU;
* влияние на загрузку страницы;
* работу на мобильных устройствах.

Практический план прототипа

Я бы строил проект в пять этапов.

Этап 1. Cubrim Web Benchmark

До интеграции в Chromium нужно проверить Cubrim именно на веб-данных, а не только на общих корпусах:

* HTML;
* CSS;
* JavaScript;
* source maps;
* JSON API;
* SVG;
* WASM;
* шрифты;
* небольшие ответы от 1 до 10 КБ;
* средние ресурсы;
* большие bundles.

Сравнение:

gzip
Brotli
Zstandard
Cubrim Web

Метрики:

compressed size
compression time
decompression time
peak memory
time to first decoded byte
energy usage

Особенно важно считать не только процент сжатия, но и пользовательские показатели:

TTFB
First Contentful Paint
Largest Contentful Paint
Total Blocking Time
page load time

Этап 2. WASM proof of concept

Собрать decoder в WASM и протестировать на реальном сайте или веб-приложении.

Это выявит, насколько декодер:

* портируем;
* безопасен;
* быстр на ARM;
* пригоден для потоковой работы.

Этап 3. cubrim reverse proxy

Создать сервер:

cubrimd

Он может:

* принимать обычные ответы;
* выбирать режим Cubrim;
* кэшировать сжатые варианты;
* поддерживать fallback;
* публиковать метрики.

Например:

Accept-Encoding: cbm, br, gzip

При поддержке Cubrim:

Content-Encoding: cbm
Vary: Accept-Encoding

Без поддержки:

Content-Encoding: br

Vary: Accept-Encoding критически важен, чтобы CDN и proxy не отдали cubrim-версию обычному браузеру. HTTP рассматривает кодировку как часть представления ресурса, поэтому разные сжатые версии должны корректно разделяться в кэше.

Этап 4. Минимальный Chromium patch

Сначала лучше ограничиться:

* Linux desktop;
* одним content coding;
* только response decoding;
* без словарей;
* без динамического подбора;
* с консервативным memory window.

После этого можно выпустить демонстрационный браузер, например:

Cubrim Browser Technology Preview

и показать один сайт, который открывается через настоящий:

Content-Encoding: cubrim

Этап 5. Публичная спецификация

Для принятия другими браузерами недостаточно патча Chromium. Нужны:

* открытая спецификация формата;
* эталонный декодер;
* тестовые векторы;
* лицензия, допускающая интеграцию;
* независимые реализации;
* fuzzing corpus;
* security review;
* web-platform tests;
* результаты на реальном HTTP Archive-подобном наборе;
* доказуемое преимущество перед Brotli и Zstd.

Как добиться поддержки всеми браузерами

Это уже отдельная многолетняя задача.

Технически путь выглядит так:

1. Опубликовать стабильную спецификацию Cubrim frame format.
2. Зафиксировать interoperable decoder behavior.
3. Подготовить Internet-Draft.
4. Обсудить предложение в IETF HTTP Working Group.
5. Зарегистрировать content-coding token в IANA.
6. Предложить implementation issue для Chromium.
7. Отдельно предложить поддержку Mozilla/Firefox и WebKit/Safari.
8. Добавить совместимые серверные реализации и CDN.
9. Доказать, что выгода оправдывает увеличение кодовой базы и attack surface.

Именно IANA ведёт официальный реестр HTTP Content Coding. Сейчас в нём находятся, среди прочего, gzip, br, zstd, а также новые словарные dcb и dcz.

Но регистрация IANA сама по себе не заставляет браузеры что-либо реализовать. Производителей потребуется убедить, что Cubrim:

* заметно уменьшает веб-трафик;
* быстро декодируется;
* безопасен;
* не дублирует уже существующий алгоритм;
* имеет стабильную спецификацию;
* не создаёт патентных и лицензионных рисков;
* поддерживается серверами и CDN;
* окупает стоимость многолетнего сопровождения.

Zstandard тоже сначала получил спецификацию и HTTP content-coding registration, а внедрение в браузерную инфраструктуру происходило отдельно.

Самая перспективная идея: не обязательно заменять Brotli целиком

Cubrim может оказаться особенно ценным как словарное веб-сжатие.

У одного сайта тысячи ответов содержат повторяющиеся:

* HTML-шаблоны;
* названия полей JSON;
* JavaScript-фреймворки;
* CSS-классы;
* API-схемы;
* стандартные компоненты.

Браузер и сервер могут заранее согласовать общий словарь, после чего сервер передаёт только различия. Именно в этом направлении развиваются dcb и dcz — dictionary-compressed Brotli и Zstandard.

Для Cubrim можно исследовать:

cubrim

обычное независимое сжатие ответа;

cubrim-d

сжатие с внешним словарём;

cubrim-site

адаптивный словарь конкретного сайта;

cubrim-session

словарь, обучаемый по ранее загруженным ресурсам с ограниченной областью безопасности.

Но shared dictionaries требуют очень осторожной архитектуры из-за рисков утечки секретов между origins и атак через наблюдение за размером сжатого ответа.

Где Cubrim может получить наибольшую пользу раньше браузеров

Входить сразу во все браузеры — максимально сложный путь. Более реалистичные первые B2B-рынки:

* собственный Chromium для корпоративной инфраструктуры;
* браузер и сервер внутри закрытой сети;
* Electron-приложения;
* мобильное приложение и его API;
* CDN edge-to-origin compression;
* синхронизация облачных хранилищ;
* передача больших JSON/data payloads;
* AI-модели и датасеты;
* обновления программ;
* расширение для собственных API-клиентов.

Например, в Electron ты контролируешь и клиент, и сервер. Там можно доказать экономию на реальном продукте, не ожидая решений Google, Apple и Mozilla.

Главный критерий

Для браузеров недостаточно показать:

Cubrim создаёт файл на 10% меньше Brotli.

Нужно показать что-то вроде:

На миллионе реальных веб-ресурсов Cubrim уменьшает передаваемые байты на 8–15% относительно Brotli, декодирует поток не медленнее X ГБ/с, начинает отдавать данные за Y микросекунд, потребляет не более Z МБ памяти и улучшает загрузку страниц на медленных мобильных сетях.

Именно такой результат может заинтересовать Chromium, CDN и IETF.

Итог: сделать собственный Chromium с Content-Encoding: cubrim можно уже сейчас, не меняя HTTP/2 или HTTP/3. Но перед этим Cubrim нужно превратить из высокоэффективного архиватора в безопасный, потоковый и очень быстрый web content codec. Лучший первый продукт — Cubrim Web Profile + reverse proxy + WASM decoder + Chromium technology preview. После доказательства преимуществ на реальном веб-корпусе уже имеет смысл идти к IETF, IANA и разработчикам браузеров.
