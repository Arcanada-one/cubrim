# Ограниченный holdout-бенчмарк Cubrim

[Дорожная карта](../../ROADMAP.md) · [Метрики производительности](../reference/performance-program.md) · [Порядок работы команды](roadmap-delivery.md)

## Назначение

`code/bench/run_holdout_bench.py` сравнивает два существующих режима (`bwt-rans`, `bwt-geomix`) с `gzip -9` и `zstd -19` на отдельном зафиксированном корпусе. Это исторический holdout-инструмент, а не вся кампания Silesia/enwik8/Canterbury и не тест всех текущих режимов Cubrim.

Обновление измерительного контура не меняет алгоритм, формат архивов или опубликованные показатели. Сначала проверяются сами инструменты и входы, затем можно проводить ограниченные измерения для ближайшего цикла дорожной карты.

## Подготовка

Нужны Python 3.10+, Git, собранный `code/cubrim-rs/target/release/cubrim`, исполняемые `gzip` и `zstd` в PATH, а также существующий `documentation/ephemeral/research/holdout/manifest.json` с замороженными файлами. Сборка — отдельная операция с согласованным бюджетом; runner сам её не запускает.

Перед запуском убедиться, что бинарник соответствует выбранной ревизии, а его сборка и параметры сохранены. `environment.code_sha` — SHA checkout, **не доказательство**, что бинарник собран из него. Бинарник дополнительно идентифицируется SHA-256 и размером; build provenance следует хранить рядом с кампанией. `working_tree_dirty` — отдельное поле, не суффикс SHA.

Нельзя заново запускать генератор корпуса ради получения лучшего результата: он меняет входные данные. Нельзя брать частные данные клиента без разрешения и размещать их в публичном репозитории. Тесты инструмента используют только небольшие синтетические подставные CLI и не читают корпус проекта.

## Проверить инструмент без бенчмарка

```sh
python3 -m unittest discover -s code/bench/tests -p 'test_*.py' -v
```

В CI эта проверка выполняется отдельно на Linux (Python 3.10 и 3.12) и macOS (Python 3.12). Не запускается сборка Rust или реальная компрессионная кампания.

## Выполнить ограниченную кампанию

Из корня репозитория, с новым идентификатором запуска:

```sh
python3 code/bench/run_holdout_bench.py \
  --report-id holdout-YYYYMMDD-revision-run1 \
  --timeout-seconds 120 \
  --total-timeout-seconds 600
```

По умолчанию — 120 секунд на дочернюю команду и общий deadline 600 секунд. Время команды ограничивается оставшимся временем кампании; на Unix таймаут завершает также потомков её группы процессов. Проверки и копирование файлов не являются прерываемыми операциями: deadline проверяется перед командами кодеков и перед публикацией, а не является жёстким лимитом для всего дискового ввода-вывода. Метаданные программ собираются отдельными командами с таймаутом 5 секунд.

Ограничение RAM, CPU и дисковой квоты задаётся средой стенда (например, лимитами контейнера) отдельно. Этот runner **не измеряет и не ограничивает peak RSS**. Более дорогой профиль требует нового разрешённого бюджета; автоматических повторов при сбое нет.

## Условия успешного результата

1. Манифест — непустой список уникальных имён обычных файлов без переходов по каталогам и симлинков. У каждого: категория, положительный целый `size_bytes` и SHA-256. Пустые файлы не входят в этот ratio-корпус: граничные входы проверяются отдельно.
2. До запуска первого кодека проверяются размер и SHA-256 **всех** исходных файлов, а также наличие всех трёх исполняемых программ. Отсутствие Zstd или gzip — ошибка, не ноль байтов.
3. Для каждой записи создаётся одна проверенная временная копия входа с исходными basename и mtime. Все кодеки получают одну и ту же копию. После каждого варианта она повторно сверяется с манифестом.
4. Команды запускаются напрямую, без shell-конвейеров. Ненулевой код возврата, пустой выход, таймаут, ошибка декодирования или несовпадение байтов останавливают кампанию.
5. Восстановление проверяется побайтово для **всех** кодеков, включая gzip и Zstd. Проверка и хеширование читают файлы порциями, а не загружают весь корпус или сжатый stdout в RAM.
6. Перед сохранением проверяется, что исполняемые файлы не сменились. Полный JSON публикуется атомарно и никогда не заменяет предыдущий отчёт. Для повторного запуска нужен новый `--report-id`.

При ошибке runner возвращает ненулевой код и пишет причину в stderr; нового итогового JSON нет. Промежуточные строки `PASS` относятся только к завершённому файлу и не заменяют успешный код выхода и конечный отчёт. Существующие исторические отчёты остаются неизменными.

## Формат результата: schema_version 2

Сохранены прежние числовые ключи `totals`, `aggregate`, `results`, поля `cubrim_<scheme>_bytes`, `gzip_bytes`, `zstd_bytes` и их отношения. Результат считается как `sum(compressed_bytes) / sum(input_bytes)`, а не среднее отношений файлов.

Добавлены:

- `schema_version: 2`, `status: complete`, `round_trip_all: PASS` — только после успешного полного прогона;
- хеш манифеста, хеш runner, SHA checkout, признак незакоммиченных изменений, пути/хеши/размеры исполняемых файлов;
- `results[].sha256`, `results[].timings[codec]` с полным размером результата и раздельными wall-time сжатия/восстановления;
- лимиты команд/кампании и список фактически выполненных команд.

Временные пути в `commands` объясняют запуск, но удаляются после проверки: для воспроизведения используются manifest, идентифицированные binaries и параметры. Новые временные измерения включают старт и наблюдение за процессом; это одиночные замеры, не профиль CPU, не статистика повторов и не основание самостоятельно объявлять ускорение. Для сравнения кандидатов выполнить заранее заданное число запусков на одинаковом стенде, сохранить разброс и отдельно измерить память.

## Следующий инженерный шаг

Выполнить один ограниченный baseline, затем собрать профили CPU/RAM для определения первого изменения кодера/декодера. Проверять стоимость выбора схем и память отдельно. Если трекер недоступен, не выдумывать ID или назначение; сохранять техническую работу в PR и восстановить связь с очередью через владельца доступа.
