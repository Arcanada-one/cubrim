# FH3-05 — Полное split-stream разложение инструкций (opcode / ModRM / SIB / displacement / immediate → типизированные потоки, каждый со своим CM-контекстом) — target: exe (mozilla/ooffice), binary

**Волна:** WAVE 3 (2026-07-22, Fable 5). **Статус:** PROPOSED, не запускалось.

## Механизм

Лёгкий дизассемблер x86/x86-64 (длина + грубые поля, БЕЗ семантики) разбирает `.text` на инструкции и **де-интерлейсит их поля в отдельные типизированные потоки**: поток опкодов, поток ModRM-байтов, поток SIB, поток displacement-ов, поток immediate-ов, поток префиксов. Вертикальная корреляция одинаковых полей (все ModRM рядом, все опкоды рядом) превращается в горизонтальную → каждый поток кодируется СВОЕЙ CM-моделью с контекстом, релевантным типу поля (для опкодов — order-1..2 по опкодам; для displacement — E8E9-класс адресная модель; для immediate — величинная). Реассемблер на декоде восстанавливает байт-точный порядок. Каждый поток — отдельная ветвь, границы/длины чарджатся.

Всё детерминированно (дизассемблер — чистая функция от байтов), fail-closed (при неразборе — fallback на raw-режим), за competitive-min.

## Чем берёт лидера

7z-LZMA+BCJ на exe: BCJ конвертит ТОЛЬКО call/jump-таргеты (E8/E9) в абсолютные, остальное жмёт LZMA как байты. Наш FH-07 E8E9-BCJ — тот же уровень. Split-stream идёт дальше: **разделяет ВСЕ поля инструкции**, так что модель опкодов не «отвлекается» на операнды, модель immediate видит чистый поток чисел, а displacement-поток — однородная адресная статистика. Патентная/академическая split-stream литература показывает: раскладка полей + PPMd на однородные потоки заметно бьёт монолитное сжатие машинного кода. Это прямой инкремент на exe-margin −9.7% поверх E8E9-BCJ.

## Научный источник (родословная + принцип)

- Split-stream патенты и работы: US 7305541 / US 6907516 «Compression of program instructions using advanced sequential correlation» — разделение полей инструкции в однородные потоки, вертикальная→горизонтальная корреляция, затем PPMD. MIPS code compression (arXiv 1205.6680) — R/I/J-разбор полей.
- **OpenZL** (Meta, 2025) — принцип типизированного графа трансформаций/потоков как современная рамка (тот же «split by field type → per-stream coder»).
- Ортогонально расширяет измеренный H-45 x86 BCJ (только call-targets).

## Оценка выигрыша (с чарджем)

- exe (mozilla dense-.text, ooffice): **−3…−8% self** поверх E8E9-BCJ-пути (грубо; лит. split-stream vs монолит на машинном коде — заметно, но Cubrim CM уже частично ловит поля через sparse-контексты, часть перекрыта). На разреженно-кодовых файлах (mozilla — code-sparse по H-45) выигрыш меньше — брать только dense-.text спаны.
- Чардж: границы инструкций/длины потоков + 1 profile-байт + стоимость дизассемблера (энкодер ×1.5–3; декодер = реассемблер, ×1.3). Дизассемблер-риск: неполный разбор → должен fail-closed в raw.

## Отличие от H-* / FH-* / FH2-*

- **FH-07 / H-45 (E8E9-BCJ)** — конвертит ТОЛЬКО call/jump-таргеты; FH3-05 — де-интерлейсит ВСЕ поля инструкции в типизированные потоки (супермножество, иная структура вывода).
- **FH-09 (BCJ2-класс)** — выносит только call-TARGET'ы в отдельный поток; FH3-05 — все классы полей (opcode/ModRM/SIB/disp/imm), не только таргеты.
- **FH-08 (x86-aware CM контексты)** — добавляет опкод/ModRM-контексты в ЕДИНЫЙ поток (данные не переупорядочиваются); FH3-05 — физически РАЗДЕЛЯЕТ потоки (реассемблинг на декоде). Механизмы комплементарны: split-stream + per-stream x86-контексты.
- **FH2-03 (ROLZ/LZ+CM)** — про parse/match-модель; FH3-05 — про раскладку полей, ортогонально.
- Не закрытая φ-ветка: перестановка — по ПОЛЯМ инструкций (структурная, реассемблируемая из чарджированных длин), не по значениям (Gotcha #7); границы = отдельная ветвь декодера (Gotcha #6).

## ВЕРДИКТ (2026-07-23, ВЕТКА-B) — NO-GO

Probe (cheap, real numbers): ooffice PE32 i386 dense .text 5 281 585 B, capstone-5 length+field split, byte-exact partition verified (538 escape-B / 0.01%). Каждый типизированный поток сжат текущим Cubrim CLI (competitive-min) и суммирован vs монолит на том же .text:

- **Cubrim: Σ streams 2 472 883 ≥ монолит 2 416 003 → +2.35% ХУЖЕ** (до charge границ/escape).
- xz -9e cross-check (backend independence): Σ 2 309 696 vs монолит 2 229 408 → +3.60% хуже.

Критерий карточки «Σ потоков ≥ монолита ⇒ вертикальная корреляция уже поймана ⇒ NO-GO» выполнен на двух независимых бэкендах. Монолитный CM/LZMA уже моделирует field-контексты в едином потоке; де-интерлейс рвёт кросс-field conditioning (opcode→operand, modrm→disp/imm size) — opcode-поток выигрывает (0.349) но проигрыш на modrm/imm/disp съедает всё. Согласуется с Gotcha #11. ooffice = dense best-case; mozilla (code-sparse tar) дал бы меньше → не мерян, вердикт устойчив. Journal-only, не БД. Harness: `probes-b/fh3_05_split.py`.
