# FH3-06 — Relocation/IAT-aware моделирование PE/ELF: un-relocate адресных dword'ов + модель таблицы импортов перед CM — target: exe (mozilla/ooffice PE), защита binary

**Волна:** WAVE 3 (2026-07-22, Fable 5). **Статус:** PROPOSED, не запускалось.

## Механизм

PE/ELF-парсер (только заголовки: секции, `.reloc`/`.rela`, import table/IAT) извлекает СТРУКТУРНУЮ информацию, которую байтовый/LZ-кодек не видит:

1. **Un-relocation:** каждая запись base-relocation указывает на dword в коде/данных, содержащий абсолютный адрес = `RVA + ImageBase`. Все эти патченные адреса делят общий `ImageBase` → вычитание базы (un-relocate) превращает высокоэнтропийные абсолютные адреса в мелкие RVA-дельты с сильной статистикой. Список позиций берётся ИЗ `.reloc` (не угадывается) — decode применяет обратный патч по той же таблице.
2. **IAT-модель:** import address table = массив указателей на импорты, часто монотонно/кластерно → дельта-кодирование + отдельный CM-контекст.

Оба преобразования обратимы из данных, уже присутствующих в файле (`.reloc`, IAT-layout), fail-closed при неразборе, за competitive-min.

## Чем берёт лидера

7z-BCJ конвертит relative call/jump (E8/E9), но **НЕ трогает абсолютные адреса в `.reloc`-патченных dword'ах и IAT** — они остаются высокоэнтропийными для LZMA. Наш FH-07 E8E9 — тот же слепой угол. Un-relocation снимает общий `ImageBase` из десятков тысяч адресов (превращая их в предсказуемые RVA), а IAT-дельта — из таблицы импортов. Это ортогонально E8E9 и берёт ту часть exe-энтропии, которую НИ BCJ, НИ split-stream (FH3-05) не адресуют. Прямой инкремент на exe-margin −9.7%.

## Научный источник (структурная база)

- PE base relocation / DELTA-механика: запись reloc = позиция dword, патчимого на `loaded_base − image_base` (offensivecraft PE Relocation Table 2022; MalwareID unpacking guide). Import Table / IAT структура — стандартная PE-документация.
- **Delta-update патенты** (US 11816471) — un-relocation table для реконструкции relocation/symbol table: подтверждает обратимость un-relocate из хранимой таблицы.
- Родословная: BCJ/BCJ2 (7z) обрабатывают только relative-branches — reloc/IAT остаются нетронуты, это известный незакрытый структурный слой.

## Оценка выигрыша (с чарджем)

- exe PE (ooffice, mozilla, где есть `.reloc`): **−2…−6% self** поверх E8E9-BCJ (грубо; зависит от ДОЛИ файла в reloc-патченных адресах + IAT — на крупных бинарях с обширным `.reloc` больше, на статически-слинкованных без reloc — ноль, fail-closed в raw). ELF-`.rela` — аналогично для PIE.
- Чардж: НУЛЕВОЙ wire-overhead для un-relocate (таблица `.reloc` уже В файле — decode читает её оттуда, ничего не передаётся сверх) + 1 profile-байт + IAT-дельта-параметры (единицы байт). Кодер/декодер ×1.2 (парсинг заголовков + патч-проход).

## Cheap probe (GO/NO-GO)

1. **Часы, без своего кодека:** скриптом распарсить `.reloc` ooffice/mozilla, применить un-relocation (вычесть ImageBase из патченных dword'ов), сжать результат ТЕКУЩИМ Cubrim CLI vs исходный .text/.data → дельта. Отдельно: IAT дельта-кодирование + Cubrim. Если un-relocated не жмётся лучше — адресная энтропия уже поймана LZ/CM, NO-GO.
2. Измерить долю байт файла, покрытых reloc-записями + IAT — верхняя граница достижимого (если reloc покрывает <2% файла, потолок мал).

Арх-риск средний (парсинг форматов; байт-точная реконструкция reloc-патча — гасится competitive-min + fallback на raw при любом несоответствии). RT-риск средний. Приоритет: **средний в exe-ветке**, дёшево проверяемо; стекается с FH3-05 (split-stream) и FH-07 (E8E9).

## Отличие от H-* / FH-* / FH2-*

- **FH-07 / H-45 / FH-09 (BCJ/BCJ2 E8E9)** — обрабатывают ТОЛЬКО relative call/jump-таргеты; FH3-06 — АБСОЛЮТНЫЕ адреса в `.reloc`-патченных dword'ах + IAT (совершенно другой класс адресов, слепой угол BCJ).
- **FH3-05 (split-stream полей инструкций)** — про раскладку полей внутри `.text`; FH3-06 — про структурные АДРЕСНЫЕ таблицы (`.reloc`/IAT), часть которых лежит в `.data`. Ортогонально и стекается.
- **FH-08 (x86-aware контексты)** — модель байтов кода; FH3-06 — модель адресных таблиц формата.
- Никакой H-*/FH-*/FH2-* не использовал `.reloc`/IAT как источник обратимого преобразования — это новый структурный слой exe.
- Не закрытая φ-ветка: таблица позиций хранится В файле (`.reloc`), wire-overhead=0; un-relocate — обратимая арифметика по известным позициям, не передаваемая перестановка (Gotcha #7 не применим).

## ВЕРДИКТ (2026-07-23, ВЕТКА-B) — NO-GO

Probe (real numbers, wire=0): ooffice PE32, ImageBase 0x1e000000, 105 000 HIGHLOW reloc, coverage 6.83%, transform RT verified. Un-relocate (вычесть ImageBase из `.reloc`-патченных dword'ов) сжат текущим Cubrim CLI vs orig:

- **Cubrim: un-reloc 2 682 682 vs orig 2 683 924 = −1 242 B (−0.046%)**; xz cross-check −684 B (−0.03%).

Оценка карточки была −2…−6%; реально −0.046% (~40–100× ниже). Причина = критерий NO-GO самой карточки: «адресная энтропия уже поймана LZ/CM». Absolute VA имеют near-constant старший байт 0x1e (кодер платит ~0), un-relocate лишь меняет его на 0x00; константный сдвиг сохраняет разности низких байт (реальную энтропию). −0.046% ниже порога окупаемости 3–5-дневной стройки PE-парсера+re-relocate+RT-риск.
