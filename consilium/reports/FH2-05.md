# FH2-05 — Пер-сегментный competitive-min: маршрутизация суб-файловых сегментов по rail'ам (OpenZL-класс) — target: exe (mozilla) vs 7z, запас на binary/code

**Волна:** WAVE 2 (2026-07-21, Fable 5). **Статус:** PROPOSED, не запускалось.

## Механизм

Сегодня competitive-min выбирает лучший rail **на файл целиком**. Гипотеза: для гетерогенных контейнеров выбирать **на сегмент**:

1. Разрез по границам tar-членов / детектированных зон (code-секция vs data vs ресурсы; детекторы e_machine/textish/soa уже есть).
2. Каждый сегмент — через мини-competitive-min (MODE_CM-exe / LZ / bwt / raw), в выход пишется 1 байт схемы + длина сегмента (чарджится).
3. Опционально: CM-состояние **продолжается между сегментами одного класса** (все code-члены кодируются одной моделью подряд — синергия с FH2-04: после similarity-сортировки одноклассовые сегменты уже соседи).

mozilla = 525 членов: Alpha-код, x86-код, данные, текстовые ресурсы — сейчас ВЕСЬ файл получает один режим, и CM-гейт (textish) на нём вообще не срабатывает.

## Чем берёт лидера

7z кодирует mozilla одним LZMA — тоже без маршрутизации. Наш ансамбль сильнее LZMA на текстовых и CM-дружелюбных кусках (CM-строка ooffice уже бьёт LZ-rail на 10%), но слабее на «чисто LZ-шных»; пер-сегментный min берёт лучшее из обоих миров там, где смесь внутри файла реально гетерогенна — и структурно не может проиграть (min + чардж заголовков).

## Научный источник (2020–2026)

- **OpenZL: A Graph-Based Model for Compression** (Meta, arXiv 2510.03203, октябрь 2025): компрессия как граф типизированных потоков с подбором кодека на поток; +15% к zstd на структурированных прод-данных Meta. Наша карточка — минимальная инстанциация того же принципа (разрез → маршрутизация → универсальный декодер по описанию в заголовке).
- zpaq (Mahoney) — per-block model selection как многолетний прецедент.

## Оценка выигрыша (с чарджем)

- **Строго ≥0 по построению** (это min); вопрос — величина. Верхняя граница меряется пробой напрямую. Грубая вилка для mozilla: **−1…−5%** (зависит от доли CM-выигрышных членов); samba −0.5…−3%; на гомогенных файлах (dickens, sao) — ровно 0, и это нормально.
- Чардж: ~3–6 Б заголовка на сегмент (525 сегментов ≈ 2–3 КБ на 51 МБ = 0.005%) + потеря межсегментного контекста у LZ (матчи через границу — вот почему сегменты крупные и почему п.3 важен).
- Скорость кодера: ×(число пробуемых rail'ов) на сегмент — смягчается ранним отсечением (как уже делает competitive-min).

## Cheap probe (GO/NO-GO)

**Часы, скрипт + существующий CLI:** разрезать mozilla по tar-членам, каждый член прогнать через `cubrim` (все режимы) отдельно, взять min по каждому, сложить + чардж; сравнить с текущим 0.308247 целофайловым. Заодно получится карта «какие члены выигрывает CM» — вход для FH-08/FH2-03. GO при ≥1.5%. Честная оговорка: по-членное кодирование теряет межчленные LZ-матчи — проба это уже включает (сумма по-членных размеров их не содержит), т.е. оценка КОНСЕРВАТИВНА; вариант п.3 (продолжение состояния) может только добавить.
